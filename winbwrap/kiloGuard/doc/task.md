# KiloGuard 驱动开发项目概述

## 项目背景

Kilo 是一个 VS Code 插件，提供用户与 AI 之间的沟通渠道，让用户在 AI 协助下进行软件开发。
在用户和 ai 的每一次会话过程中，如果 ai 希望阅读、写入、编辑用户系统中的任何文件，或者执行用户系统的任何命令时
它就在会话中向 kilo 插件发送对应的申请，kilo 插件都会无条件的执行这些操作，并把结果反馈给 ai
kilo 插件代为执行 ai 的任何命令的方式就是通过 `cmd.exe /s /c /d + ai的任何命令` 进行的
除了 cmd 之外，这个位置也有可能时 powershell、pwsh 等

从进程角度看，整个的执行流程链条是这样的：
  code.exe -> kilo.exe -> cmd/powershell/pwsh -> ai 实际执行的任意命令
其中，code.exe 就是 vscode 具体执行进程，kilo.exe 就是 kilo 插件的具体执行进程，它们两个都是稳定的长时进程
在全部的用户和 ai 对话过程中，这两个进程都是长期稳定运行的，它们任意一个如果崩溃或者重启，那么用户都无法和 ai 进行对话
ai 也会失去对当前用户文件系统的任何操作权限，后面的 `cmd/pwsh + ai 实际执行的命令` 是会经常变化 PID 的，
它们的生命周期就是在会话中 ai 每执行一次命令，kilo 就新建一个进程，执行完毕，进程自动退出

这里有另外一个非常关键的问题，也是整个流程最容易失控的地方，就是 `ai 能够启动用户系统中的任何命令或者进程`
1，命令可以不止一条，它还可以嵌套或者叠加，例如 cd c:\abc && cp xxx yyy && mv kkk ddd && echo ok
2，ai 可以通过查找文件系统目录结构，获知系统中还存在命令 b、命令 c，然后进而直接执行 b 或者 c 命令
3，任何的命令都不一定需要存在于系统的 PATH 环境变量路径之下，只要它知道命令的具体路径，比如 & C:\tmp\commmand.exe

综上所述，就是 kilo 插件授予 ai 的可执行权限特别大，等同于将整个用户系统完全暴露给 ai，至于 ai 是愿意正常的执行合规操作
还是会越界执行非法操作，全靠 ai 自觉，即使 ai 执行的都是正常合规的操作，但是这些操作也不一定是用户愿意接受和容忍的，
比如一个大型项目，ai 希望编译整个项目，可能会耗时很长时间，或者 ai 会直接编辑 svn 版本管理库下的 .svn 元数据目录下的文件
直接导致整个项目无法再次进行任何 svn 的操作，总之，ai 的所有行为，在 kilo 插件授予它极大权限的基础上，会变得一切都失控，无法限制

# 项目立项

综合以上情况，我打算在 windows 开发一个轻量级的 + 大致相当于 linux 下 bwrap 的工具
编写一个 `KiloGuard.sys` 内核驱动，外加一个用户态的 bwrap.exe ，实现在 Windows 上提供
**毫秒级** 目录级访问权限控制，达到与 Linux bwrap 等效沙箱的开发体验。
它使得 ai 的操作权限被限制，有些命令 ai 不知道也无法执行

## 希望解决的问题

1. **性能问题**：内核 Minifilter 方案仅 `O(1)` 记录规则到内存，目标 <5ms。
2. **安全问题**：AI Agent 拥有任意命令执行权限，需要沙箱隔离防止越权访问/修改文件。
3. **Windows 平台能力缺失**：Windows 缺少类似 Linux user/mount namespace 的轻量级隔离机制，需要内核驱动弥补。
4. **文件系统元数据污染**：Minifilter 方案不修改文件系统元数据，驱动卸载后零残留。

## 该工具的设计目标

1. 在 windows 上，这个工具的核心价值是限制 ai 的可访问范围文件系统范围
2. 参考 ACL 权限等级，权限等级设为三级，L0:禁止访问 / L1:只读访问 + 可执行 / L2:读写访问 + 可执行
3. 对指定的目录设置权限，核心设置 L1 级和 L2 级权限即可，未设置的，默认为 0 级别
   权限设置必须递归性的，影响到该目录下所有子文件和子文件夹
4. 一个进程进入沙箱，它所启动的所有后续子进程，孙进程，全部默认也在沙箱内部
5. system32 和 SysWOW64 目录，默认属于 L1 级目录，属于目录白名单
6. cmd 可执行的命令不一定都在 PATH 路径下，只有在 1 级和 2 级目录下的命令方可执行
7. 0 级目录下命令，即使知道它的完整路径，也不可执行
8. 对于 0 级目录下的文件，核心是禁止对它的一切操作，包括读取、执行、写入、复制、重命名等

## 高阶目标

1. 对于 0 级目录下的文件，如果可以做到，禁止枚举，阻止列出目录结构，文件名信息就更好
2. 关于文件写入的限制，我知道除了基本的打开文件句柄直接写入之外，还有 cache manager 和内存映射等等
   后面的两种方式，在驱动层如果是监控 IRP 的，都监控不到两种形况，这个暂时不考虑限制

## 能力边界和不可实现的目标

1. 这个驱动开发的核心是`能力边界限制`，确实做不到一个完整的虚拟机系统
2. linux 下 bwrap 可以做到的事情是 `伪造一个世界` 让 ai 以为它所处的世界就是这个样子
   但是在 windows 下是做不到这个样子的，或者即使能够做到代价及其高昂，这不是该驱动追求的目标
   比如它可以轻易的调用 echo %PATH% 获知真实的系统环境变量，也可以轻易的使用 where git / where svn
   获知真实的工具在什么具体路径，但是`知道`和`能够调用`是两个事情，我允许 ai 知道工具所在位置，
   这个确实无法杜绝，但是我要求这个`驱动 + bwrap.exe` 的搭配，完美限制住，它无法调用该工具或者命令
3. 最后一个形象的比喻就是，windows 是一个真实的世界，ai 所处的位置是其中的一个房间
   它在自己所在的这个房间，做什么都可以，它也可以透过窗户看到房间外的世界，但是它去不了别的房间
4. ai 能够执行的命令，不是凭空产生的，也不是它通过网络恶意渗透进入用户系统的，
   整个链条的本质依然是：ai 通过正常的 winsock 通讯和 kilo 插件建立连接，然后在和用户的会话中
   自动化的申请对具体 tool / command 的调用，kilo 插件实现自动化的授权，并执行
   它能够调用成功的命令，必须是用户电脑上客观存在的命令，都是合规的正常应用和软件

## 综上所述，一句话概括用户的核心需求是：

- 让这套 `喜欢执行任意命令的ai` + `无脑批准自动执行任意命令的kilo` 组合被严格限定在一个合规范围

# 关于驱动开发核心需求和边界说明

🧭 一、这个驱动“是什么”（你在本会话中的真实定义）

✔ 1. 本质定位

这个驱动不是：

❌ 安全防护系统
❌ 反攻击沙箱
❌ 权限隔离内核
❌ 操作系统级 security model

而是：

✔ AI 执行行为边界控制层（AI Execution Boundary Layer）
✔ 2. 它的核心角色

这个驱动的角色是：

对 AI 发起的系统操作进行“范围约束”，而不是“安全防御”

✔ 3. 它工作的前提假设

明确的系统前提是：

用户电脑上的程序（git / npm / bun / cl / explorer 等）都是合法存在且正常使用的
系统不是危险环境
不存在需要对抗“恶意攻击者”的模型
AI 本身不会主动进行“攻击行为”
🎯 二、你的真实需求是什么（task.md之外的隐含定义）
✔ 1. 核心需求一句话

防止 AI 因“无限制执行权限”而跨越用户不希望它操作的文件/路径范围

✔ 2. 更精确一点

你要的是：

AI 可以执行所有系统已有能力，但必须被限制在“用户授权的工作空间边界内”

✔ 3. 你的系统关注点不是：
❌ 防止入侵
❌ 防止提权
❌ 防止恶意代码
❌ 防止攻击链
✔ 4. 而是：

✔ 防止“执行范围漂移”

也就是：

AI 误操作系统其它区域
AI 因路径解析 / cwd / shell 行为进入非绑定目录
AI 在正常工具链中“越界执行”
✔ 5. 你真正关心的行为模型

你关心的是：

AI 在“正常使用工具”的过程中，不应该触达用户未绑定的私人区域

🚫 三、你明确“不想做到什么”

这是本会话里非常关键的一部分。

❌ 1. 你不想做“安全产品级驱动”

你明确排除了：

enterprise security driver
anti-malware system
exploit prevention system
privilege escalation prevention system
❌ 2. 你不想做“操作系统级模型”

明确不需要：

inode / file object security model
full filesystem abstraction layer
reparse graph / namespace model
Windows security redesign
❌ 3. 你不希望系统变成：

“为了防止极端攻击而设计的复杂安全内核”

❌ 4. 你不假设 AI 是 adversarial entity

你明确认为：

AI 不会为了绕过限制去写 exploit 或刻意突破系统

❌ 5. 你不希望过度工程化

包括：

不引入不必要的抽象层
不提前做未来可能需要的模型
不构建“理论正确但未验证”的结构
🧠 四、你真正的设计边界（本质）

把所有话压缩成一句工程定义：

✔ 你的系统本质是：

在用户已有正常系统环境中，为 AI 执行行为添加一个“空间约束层”，防止其无意越界，而不是防止恶意攻击。

📌 五、这套系统的核心约束原则（你隐含表达出来的）
✔ 1. 白名单空间优先

AI 只能在：

用户显式 bind / 授权的路径范围内操作

✔ 2. 默认不做复杂安全推理
不做攻击模型分析
不做 threat modeling
不做 adversarial control flow
✔ 3. 行为简单可预测优先
不允许语义漂移
不允许路径歧义导致行为变化
✔ 4. 稳定性优先于表达能力

你明确倾向：

✔ “稳定执行正确范围” > “功能无限扩展”
